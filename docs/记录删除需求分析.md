# 记录删除功能 · 需求分析

> 结论先行：**建议做，且优先级中等偏上**。数据层（墓碑删除、云端同步标记）已经就绪，
> 只缺一个安全、可控的交互入口。当前用户遇到的真实痛点是——导入错了旧版本解析的记录后，
> 没有任何办法清掉它，只能"看着它一直躺在列表里"。

## 1. 现状盘点

| 能力 | 状态 | 说明 |
| --- | --- | --- |
| 数据层删除 | ✅ 已有 | `repo.removeActivity()` 做墓碑删除（`deleted = Date.now()`），列表、统计立刻消失 |
| 恢复 | ✅ 已有 | `restoreActivity()` 把墓碑清零 |
| 云端同步 | ✅ 已有 | 备份层靠墓碑把删除标记推到两端；`unsyncedMeta()` 会识别"已删除但云端还有" |
| 云端物理清理 | ⚠️ 部分 | 删除标记推上去后，云端 manifest 里仍有轨迹载荷，依赖对账逻辑清理 |
| 轨迹 / 原文件清理 | ❌ 未接 | `deleteTrack()` / `STORE.files` 不会被删除入口触发，本地空间不回收 |
| 交互入口 | ❌ 没有 | 记录卡片只有"创作"，无长按/右键/编辑菜单，用户无法发起删除 |
| 回收站 / 撤销 | ❌ 没有 | 误删无法自救（墓碑在本地库里，UI 层看不到） |

## 2. 为什么要做（用户价值）

1. **纠错**：旧版本解析错误产生的记录（距离/时长不对）现在无法清除，只能永远留着；
   解析算法每次升级，用户都需要"删掉旧记录 → 重新导入"。
2. **隐私**：轨迹是敏感数据，用户应有"从这台设备移除"的能力。
3. **整理**：华为数据副本一次导入几百条，门槛过滤（已上线）挡住了大部分，
   但仍会有漏网的通勤、测试记录需要手动清理。

## 3. 建议的交互方案（实现时参考）

- **入口**：记录卡片长按（移动端）/ 右键（桌面端）弹出操作菜单：`创作视频`、`导出`、`删除`。
  单独放一个"删除"小按钮误触率高，不推荐。
- **确认**：删除前弹确认卡（现有 `showAlert` 风格），文案写清楚影响范围：
  「将删除本条记录及其轨迹；若已开启备份，云端副本也会在下次同步时移除。」
- **撤销窗口**：删除后 Toast 提供「已删除 · 撤销」按钮，10 秒内可撤（墓碑天然支持）。
- **回收站（二期）**：设置页加"最近删除"，列出墓碑记录，30 天后由维护任务
  连带 `deleteTrack()` / 原文件一并物理清理。一期可先不做，只保留撤销。
- **批量**：数据副本导入场景下，列表筛选（如"来源：华为"）+ 多选删除是真实需求，
  建议二期与回收站一起做。

## 4. 数据与备份的一致性要求（验收标准）

1. 删除后：列表、统计（总数/总里程）、筛选 chips、合并候选列表**立即**不再出现该记录。
2. 墓碑被推到 GitHub/Gitee 后，`backup` 状态流转正确，不会出现"删了又同步回来"。
3. 两端同时删/一端删一端改：以 `updated` 新者为准（现有 manifest 合并规则已满足，需回归）。
4. 物理清理（二期）后，`loadActivity` 抛"记录不存在"，不得崩溃；缩略图、原始文件一并回收。
5. 合并记录的 `mergedFrom` 指向的父记录被删时，合并记录仍可打开（父 id 仅作来源展示，不做外键约束）。
6. 撤销操作恢复列表原位置与备份状态位。

## 5. 风险与对策

- **误删不可逆**：一期用"撤销 Toast"兜底；二期回收站落地后再考虑直接删。
- **与云备份竞争**：删除时若正在上传，`sync` 层要对墓碑短路（检查 `deleted > 0` 再跳过上传），需要回归测试。
- **统计缓存**：`repo.invalidate()` 已在删除路径上，注意新增入口别绕过 `removeActivity()` 自己写库。
- **合并记录连锁**：不级联删除合并产物，只在确认弹窗里提示"该记录是某条合并路线的来源段"。

## 6. 工作量评估（实现时）

一期（入口 + 确认 + 撤销）：records.ts 卡片长按事件、一个操作菜单组件、
`removeActivity` 已有 → 前端 1 个文件 + 少量 CSS；二期（回收站 + 物理清理 + 批量）：
需要新的 UI 面板与清理任务，涉及 tracks/files 两个 store。
