# FIT MOTION 优化方案（2026-11-09）

> 顺序原则：先修「数据正确性」（影响所有页面展示）→ 再修「视频观感」→ 记录页交互 → 备份与安全 → 架构清理 → 新功能。
> 每条都标注了代码核实结论，确认问题属实后才进方案。

## 一、数据正确性（优先修，改动波及列表页 + 创作页 + 备份）

### 1. 平均速度计算错误 —— ✅ 问题属实
**核实**：`src/fit/activity.ts` L219-262。`movingSec = session.timerTime ?? actualDuration`，而 `actualDuration` 在 `timerTime` 缺失时回退到 `elapsedTime`（总耗时）。也就是说：**FIT 文件没有 `total_timer_time` 时、以及 GPX/TCX/华为 JSON（根本没有 timerTime 概念）全部走「距离 ÷ 总耗时」**，停车休息时间全被摊进去，均速偏低。列表页 `meta.avgSpeed` 与创作页共用这条链路，所以两处都不对。
**方案**：
- 引入真正的「运动时长」（moving time）：
  - FIT：优先 `total_timer_time`；缺失时按轨迹点间时间窗估算（如 30 秒窗口内位移 ≈ 0 判为停留，累加移动时间）。
  - GPX / TCX / 华为：统一用点间停留检测估算。
- `avgSpeed = distance / movingTime`，列表页与创作页共用（改一处 `buildActivity` 即可）。
- 已入库旧记录的 `meta.avgSpeed` 是导入时算好的：增加一次性迁移任务（打开记录时惰性重算，或版本号触发全量重算）。
- 创作页数据面板增加「总时长」（elapsed）字段，与「运动时长」并列显示；`avgSpeedAvailable` 为 false 时照旧隐藏。

### 2. 重复导入不替换、华为 JSON 信息更全却被跳过 —— ✅ 问题属实
**核实**：`src/store/repo.ts` L211/L224。文件指纹或运动指纹命中后直接返回 `duplicate-file` / `duplicate-motion` 并跳过，没有任何替换路径。华为 JSON 常带心率，FIT 没有，导致「信息少的旧记录一直占位」。
**方案（已确认：自动按数据完整度决定，无需用户选择）**：
- 命中重复时计算两边的**数据完整度评分**，逐项判分：
  - 心率（max/avg 有值）+2、海拔（有值）+1、速度字段（有值）+1、热量（有值）+1、轨迹点密度（点数/公里，≥5 点/km）+1、时长与距离非估算（session 原生字段）各 +1。
- **新数据评分 > 旧记录 → 自动替换**：沿用原记录 id（云端 `tracks/<id>.fmt` 直接覆盖，备份 commit 不膨胀），更新 meta 与轨迹 blob，`meta.updated` 刷新 → 现有对账同步自动把新数据推上云端，协议零改动。
- 替换后 toast 明确提示：「已用华为数据替换（新增心率等 N 项信息）」。
- 评分相同或新数据更差 → 不替换，提示「已存在同名运动，数据更全，未替换」。
- 完整度评分函数放 `store/fingerprint.ts` 旁，导入页与批量导入共用；批量导入一次华为 JSON 撞多条旧记录时逐条自动判定，不打断流程。

### 3. GPS 漂移点 —— ⚠️ 部分已处理，需补全
**核实**：华为导入已有飞点过滤（`src/import/huawei.ts` L254-269：物理不可能的相邻距离），`src/fit/activity.ts` L161 有「离开又立刻返回」的 GPS 跳变剔除。但 FIT/GPX/TCX 没有逐点漂移过滤，且「甩到极点再回来」之外的单向漂移没人管。
**方案**（导入后统一走一遍 `sanitizeTrack`）：
- 速度上限法：相邻两点距离/时间差 > 物理可能（骑行 > 130 km/h、步行 > 40 km/h，按运动类型取阈值）判为漂移点，丢弃并用前后点插值补齐时间。
- 精度字段法：FIT 有 `position_accuracy` / GPS 优势星级时，低精度点降权或丢弃。
- 孤立偏移法：点偏离局部路径趋势 > 300 m 且下一秒回到轨迹 → 剔除（现有逻辑扩展成双向滑窗）。
- 处理结果入库前打印「剔除 N 个漂移点」，日志留痕可回溯。

## 二、视频观感

### 4. 视频时长过长 —— ✅ 问题属实
**核实**：`src/render/stage.ts` L62-68。公式 `(7 + 0.36×km) × paceFactor`，封顶 `RUN_MAX=40s`；再加封面 1.1s + 起步 + 片尾 3.2s 等固定段。67 km：6+0.36×67=31.1s×pace + 固定段 ≈ 38~42s，与你实测吻合。
**方案**：换「对数感知曲线」，短途不赶、超长不再线性暴涨：
- 新公式（初值，开发时用 `tools/duration-model-test.mjs` 调参）：
  `runDuration = clamp(8 + 7.5 × ln(1 + km) / ln(1 + 100) , 10, 26) × paceFactor`
  - 3 km ≈ 11s、10 km ≈ 15s、30 km ≈ 20s、67 km ≈ 23s、100 km ≈ 24.5s、200 km 封顶 26s。
- 固定段（封面/片尾/停顿）同步压缩：片尾 3.2→2.4s，总固定时长从 ~6.5s 降到 ~5s。
- 67 km 成片从 42s 降到 **~28s**；`RUN_MAX` 从 40 降到 26。
- 预览截图工具回归：改完跑 `tools/final-shots.mjs` + `check-parity.mjs` 对齐 TS/Java 双渲染。

### 5. 轨迹尾部「贪吃蛇式缩短消失」 —— ✅ 问题属实（当前设计如此，但观感是 bug）
**核实**：`src/render/stage.ts` `drawRoute`（L1132 起）。走线时用 `localIndex` 把已走过部分从路径里裁掉，只画当前点到前方 look-ahead 的虚线；第一视角镜头一移动，身后的轨迹就从画面上整段消失，像贪吃蛇吃掉尾巴。
**方案**：
- 已走过部分改为**持久保留**：用「完整路径 + 世界坐标绘制」，镜头后方的轨迹自然移出画面（而不是被裁掉），骑回来或镜头回扫时能看到走过的地方。
- 走过段降透明度（约 45%）+ 未走段保持亮色 + 前方 look-ahead 虚线不变，层次反而更清楚。
- 同步改 Java 侧 `NativeScene` 的对应绘制，保持双渲染一致（本项目既有约定）。
- 内存安全：走过段复用抽稀缓存（`overviewRouteCache` 思路），不加新的大数组。

### 6. 预览倍速与导出倍速联动 —— ✅ 可行
**核实**：导出倍速已存在（`main.ts` L386-389，`exportSpeed` 1~5 档，成片时长=原时长÷倍速）；预览播放是另一套 `playbackRate`。两者目前独立。
**方案**：
- 点击预览倍速按钮：`exportSpeed = 预览倍速`（单一状态源），并 `playhead = 0` 从头按倍速播放。
- 导出倍速卡（`data-es`）与预览按钮显示同一个选中态，改一处两边高亮。
- 导出即按当前选中倍速出片，行为可预期。
- 注意音乐：现有设计「背景音乐按成片时长原速渲染」保持不变。

### 7. 创作页 UI 调整（一批小改）
- **分段数据**不在创作页展示：隐藏对应 section（`main.ts` L888、L825 的展开状态一并清掉）。
- **静帧预览移除**：删 `isStill` / `t=` 分支（L145、L237-242）与「渲染静帧预览…」链路（L1405）。
- 按钮重排（自上而下）：导出视频（主按钮）→ **导出倍速** → **导出 GPX / 导出 TCX / 导出数据长图**（名称由「数据长图」改为「导出数据长图」）→ 最底部 **清除地图缓存**（原「清地图缓存」改名）。
- `index.html` 里按钮 DOM 顺序同步调整。

## 四、备份与安全

### 12. 备份页输入行：可长按粘贴、不唤起华为安全键盘 —— ✅ 已定位
**核实**：`src/ui/panels.ts` L341，token 输入框 `type: 'password'`，`dialog.ts` L82-86 渲染成 `<input type="password">`。**EMUI 对 password 型输入框强制唤起华为安全键盘**，且安全键盘禁用长按粘贴。
**方案**：
- token 字段改 `type="text"` + `inputmode="url"` + 等宽字体 + 「显示/隐藏」眼睛按钮（隐藏态用 CSS `-webkit-text-security: disc`，不是 password 输入框，不触发安全键盘）。
- 仓库行加 `autocapitalize="off" autocomplete="off" spellcheck="false"`，长按粘贴恢复正常。
- 顺带检查所有 `fm-input`，确保没有其他 password 型字段。

### 13. 百度网盘备份（已调研接口）
**调研结论**（百度网盘开放平台 pan.baidu.com/union）：
- 需要注册开发者并**创建应用**拿 API Key/Secret（应用需填写、可能要审核——这是最大门槛）。
- OAuth2 授权：`access_token` 有效期 1 小时，`refresh_token` 刷新。
- 上传统一走 xpan 三步分片：`precreate` → `superfile`（逐片上传）→ `create`（合并）。普通用户单文件上限 **4GB**、分片 ≤1024 片、单片上传需在超时窗口内完成（放宽后实测约 30 分钟/片）。多年华为 JSON 大文件完全够用。
- 上传域名可动态获取（`/rest/2.0/xpan/multimedia?method=uploadcurl`），提速。
- **申请门槛（已查证）**：官方没有「完全不注册开发者」的接口。但**个人开发者入驻门槛很低**：百度开发者账号 + 个人身份证号 + 邮箱/手机号实名，**审核即时完成、免费、可创建 2 个应用**，基础能力（上传/下载/管理文件）个人开发者全都有。这是推荐路径，一次性 5 分钟动作。
- **不申请开发者的替代路径**（已调研）：
  1. ❌ 非官方接口（bypy / BaiduPCS-Go 用 BDUSS cookie 走旧 PCS 接口）：bypy 已进入维护模式、接口靠逆向、有频控与封号风险，不适合集成进要长期使用的 App，不建议。
  2. ✅ **WebDAV 通道（推荐的零申请方案）**：不做百度专用适配，而是加一个**通用 WebDAV Provider**——坚果云个人版无需任何开发者申请，网页设置里生成「应用密码」即可用（免费 1GB/月上传流量），任何支持 WebDAV 的网盘/自建服务（群晖、Alist 等）都能直接接。协议标准化，实现成本比百度接口还低，顺带覆盖更多用户。
  3. 结论：**百度走个人开发者实名（门槛低、4GB 大文件、官方稳定）；WebDAV 作为零申请的通用通道并行提供**，导入自动备份开关对两条通道都生效。
**方案**：
- `backup/adapter.ts` 增加 `BaiduPanProvider`，与 GitHub/Gitee 同一 Provider 接口：`manifest.json` + `tracks/<id>.fmt` 的目录结构不变，网盘里建 `/apps/fitmotion/` 目录。
- 对账逻辑完全复用（manifest 是索引、谁新推谁、墓碑删除）。
- 备份页加「百度网盘」绑定卡：点授权 → WebView 打开百度 OAuth 页 → 回调拿 code → 换 token，token 存本机。
- 导入时自动备份做成**开关**（默认关）：导入落库后入队静默上传，大文件分片+断点续传（precreate 返回的已传分片表天然支持续传）。
- 风险提示：百度接口要求 HTTPS、普通用户免费配额有限（频次限制按异常行为判定）；上架商店前该功能只能算「个人增强」。

### 14. 端到端加密备份 + 本地加密
**方案**（算法选型：**AES-256-GCM + PBKDF2**，纯 WebCrypto 实现、原生层零依赖、速度足够快）：
- 首次在手机上设置「备份密码」（不上传、不云同步）：
  - 密钥派生：PBKDF2-HMAC-SHA256，60 万次迭代（约 0.3~0.5s，只在设密码/解锁时算一次），盐随机 16B。
  - 每个文件独立 12B 随机 IV → AES-256-GCM 加密（认证加密，防篡改）。
- 流程：gzip（现有 codec）→ AES-GCM → base64 上传；云端只有密文，**百度/GitHub 服务器均无法解密**，即端到端。
- 本地数据加密：派生密钥本身用 **Android Keystore** 包一层后存本机（App 数据目录），IndexedDB 里的轨迹 blob 写入前加密（写入时加密，读时解密，1MB 轨迹加解密 <50ms，无感）。
- 改密：只重加密「密钥包裹层」（Keystore），不用重加密全部轨迹——因为数据密钥不变，仅包裹层换。
- 忘记密码 = 数据不可恢复，设置页明确警示。
- 兼容：加密开关默认关；开启后 GitHub/Gitee/百度三条通道都走密文，manifest 里的明文统计字段可选择一并加密或保留（保留便于列表恢复，方案里建议保留并文档说明）。

## 五、架构清理与性能（其中第 15 条已逐一核实）

### 15. Android 三项遗留 —— ✅ 全部属实
**核实结果**：
- **Surface 桥无人调用**：`MainActivity.java` L504-534 有 `beginSurfaceExport` / `copySurfaceFrame` / `finishSurfaceExport` 三个 `@JavascriptInterface`，全项目 JS 侧（main.ts / web 包）**零调用点**，只有类型声明残留。`SurfaceExporter.java`（150 行）只被 MainActivity 引用。属实。
- **versionName 脱节**：`AndroidManifest.xml` 固定 `versionCode=1 / versionName=1.0.0`，网页/JS 无版本号来源，每次发版 APK 都不变。属实。
- **targetSdk 30 偏老**：manifest L7 `targetSdkVersion=30`（Android 11）。Google Play 现要求 targetSdk ≥ 34，国内主流商店要求 ≥ 30~33 且逐年抬升。属实（个人侧载没问题，上架必被拒）。
**方案**：
- 删除 `SurfaceExporter.java` + MainActivity 三个桥方法 + main.ts 里对应的类型声明（L39-42）。
- 版本号单源化：`package.json` 加 `version`，`build-web.mjs` 注入 JS 全局 `FITMOTION_VERSION`，`build-apk.mjs` 用同一值改写 manifest 的 versionName/versionCode（versionCode = 日期流水，如 20261109）。
- targetSdk 升 34：回归测试点=MediaStore 保存（`Download/FIT Motion/`）、SAF 兜底、文件选择器、通知（导出进度）；`ExportService` 需补 foregroundServiceType 声明（Android 14 要求）。minSdk 29 保持。
- **网页端废弃范围（已确认执行）**：APK 本身跑同一份 Web 包，删的是「浏览器独立使用」路径，代码主体保留：
  - 删：`web-dist/`、`public-apk/` 里的网页演示页（html）、README 的浏览器直开说明与 `python -m http.server` 用法、Gitee CORS 兜底相关注释。
  - **保留 `apk-download/`**：这是 APK 的手机下载入口（fitmotion-apk-download 部署链路），属于分发渠道不属于「网页端使用」，删了会丢手机下载链接。
  - `README_EXPORT.md`、`prototype/` 视情况归档或删除。

### 16. 冷启动与渲染/内存保护 —— 有方案，按性价比排
**核实**：单文件 `dist/index.html` 内联约 1.7MB；`BITMAP_CACHE_LIMIT` 只限瓦片张数，无字节上限；500MB 轨迹缓存上限有了（LRU 淘汰），设置页有「清除地图缓存」但无占用显示与单条清理。
**方案**：
- **冷启动**：esbuild 拆两包——首屏必需（外壳+记录列表）先行 `<script defer>`，渲染管线（stage/vector-map/audio 合成器）懒加载（WebView file:// 下用动态 `<script>` 注入而非 import()，规避 file:// 限制）；目标首屏体积 <600KB。另加启动骨架屏，观感首屏 <300ms。
- **渲染内存**：跟随镜头层点数上限（显示用抽稀到 ≤1500 点，导出用全量——overview 已这么做，follow 层补齐）；位图缓存加总字节上限（如 256MB，超限按 LRU 释放）。
- **瓦片缓存 UX**：设置页「清除地图缓存」行上方加当前占用（`navigator.storage.estimate()`）；记录详情加「清除本条轨迹缓存」（单条 LRU 强制淘汰 + 回源标记）。

### 17. 一键分享微信 / 抖音 —— 可行性：✅ 推荐「系统分享面板」方案，不做官方 SDK
- 不接微信开放平台/抖音 SDK（都要企业资质+审核+签名校验，个人 APK 走不通）。
- 用 Android 标准分享：`Intent.ACTION_SEND` + `FileProvider` 暴露 mp4 长图，`video/mp4` 类型 → 系统分享面板里微信（发给好友/文件传输助手）、抖音（上传草稿）都能接收。
- 创作页导出完成后，在「已保存」提示旁加「分享」按钮 → 拉起面板。微信对未认证应用分享图片有限制，视频 mp4 走聊天路径实测可用；抖音接收 ACTION_SEND 的视频没有门槛。
- 兜底：面板无目标 App 时提示安装。

### 18. 一键生成「年度骑行回顾」

- **视频**：复用 stage 时间线——片头插 4 秒「年度数据卡」（复用结果面板组件），接当年最长一趟的成片，片尾年度海报帧。放在长图之后迭代。
