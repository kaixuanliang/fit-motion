# 备份空间预算与上限

> 结论先说：**当前每条约 120~150 KB（12,000 点的骑行），Gitee 500 MB 约能存 3,500~4,200 条，GitHub 1 GB 约能存 7,000~8,400 条。**按 300 条/年，Gitee 大约 12 年填满。真正需要担心的不是轨迹本身，而是「清单每改一次就新增一个 Git 版本」和「删除不释放历史」这两件事——前者已修掉空写，后者无法通过 API 回收。

## 一、一条记录在云端到底占多少

实测（`tools/storage-budget.mjs`，1 Hz 采样 + GPS 抖动 + 海拔 + 心率）：

| 点数 | 本地内存 | 紧凑二进制 | 写进仓库的文本 | 同点数 GPX | 每点成本 |
|---|---|---|---|---|---|
| 4,000 | 120 KB | 60 KB | **56 KB** | 480 KB | 14.0 B |
| 12,000 | 360 KB | 180 KB | **147 KB** | 1.44 MB | 12.3 B |
| 20,000 | 600 KB | 300 KB | **229 KB** | 2.40 MB | 11.5 B |

也就是说：**约为同内容 GPX 的 1/10**，每点 12 字节左右。用户实测 23 条 / 1,860 km = 2.8 MB，折合 122 KB/条，与上表一致（平均每条约 1 万点）。

## 二、现在做了什么（三道压缩 + 两道隔离）

1. **只存推不出来的字段**：距离、速度都在打开时按经纬度重算，不落盘（每点省 8 字节）。
2. **量化**：经纬度 i32（1e-7 度，约 1.1 cm，远小于 GPS 误差）、海拔 i16×10、心率 u8、时间戳存「首点 f64 + u32 秒差」。
3. **gzip + base64**：gzip 后体积约为紧凑二进制的 0.8 倍；base64 再加 33% 文本开销（换取跨 GitHub/Gitee 的安全搬运）。
4. **清单与正文分离**：清单只有名字、距离、缩略图、统计，列表页不下载轨迹；换手机装完连网就能看到全部历史。
5. **本地不背历史**：本地轨迹是 LRU 缓存（上限 500 MB），只淘汰已经备份过的记录，索引和缩略图始终留着。

## 三、容量测算

| 场景 | 每年占用 | Gitee 500 MB | GitHub 1 GB |
|---|---|---|---|
| 150 条/年 | 21 MB | ≈ 24 年 | ≈ 48 年 |
| 300 条/年 | 42 MB | ≈ 12 年 | ≈ 24 年 |
| 500 条/年 | 70 MB | ≈ 7 年 | ≈ 14 年 |

两端是**完整镜像**，不是冷热分层：同样的数据各存一份，任何一端能连上就够用，配额也各自独立计算。

## 四、这次修掉的两个吃空间的问题

1. **空同步也会写一版清单**：`snapshot()` 原来用 `Date.now()` 当清单时间戳，导致每次点「同步」序列化出的文本都不同，即使一条记录都没变也会 `put` 一次。Git 里每次 `put` 都是一个新版本。现在改用「最新一条记录的 updated」当版本号，`tools/space-budget-test.mjs` 验证：无变化同步的清单写入次数为 **0**。
2. **清单里混进了本机状态**：`where`（各端推到哪一版）、`backup`、`opened`、`purged` 原来会一起写进云端。它们对换设备毫无用处，却让两端互相看对方时间戳反复改写（一次同步两边各写两版），还让每条多出约 80 字节。现在清单只保留跨设备有意义的字段。

## 五、已知的结构性风险（还没解决）

| 风险 | 影响 | 现状 |
|---|---|---|
| **Git 历史不随删除释放** | 删除只把文件从当前树里去掉，旧 blob 仍在历史里，配额不会降 | 无 API 可回收；只能新建仓库重传，或在网页端做一次历史重写 |
| **清单体积随条数线性增长** | 每条约 1.3 KB（其中缩略图 SVG path 约 0.7 KB），4,000 条时约 5 MB；每改一次就新增一个版本（Git 会做 delta 压缩，实际增量远小于 5 MB，但仍在长） | 已消除空写；未做分片 |
| **base64 多 33%** | 纯文本传输的代价 | 换二进制要走 Git Data API，Gitee 兼容性差，暂不做 |
| **原始文件不上云** | FIT/GPX/TCX 原件只在本地 | 有意为之（原件比压缩轨迹大一个数量级），导出时按轨迹重新生成 |

## 六、什么时候该动下一刀

- **> 1,500 条**（清单 > 2 MB）：把清单按年份分片（`fitmotion/index/2026.json`），本地缓存分片版本号，只有变化的年份才重写。收益：单次写入从 O(全部) 降到 O(当年)。
- **> 3,000 条或容量显示 > 85%**：给老数据加可选降采样（例如 2 年前的记录按 5 秒间隔存），体积再降 60~70%，轨迹形状与统计几乎无差别。
- **真要换仓库**：新建空仓库 → 绑定 → 全量同步一次（清单会重建，轨迹按需上传），历史清零、配额回收。

## 七、给用户的可见信号

- 备份页每家一张容量条，> 85% 变红并提示；> 96% 时**同步直接停止上传**并说明原因，不再一条条撞 4xx。
- 新增「空间预算」卡片：平均每条体积、两端分别还能再存多少条、按现有节奏折算多少年。
- 同步完成的提示带上本轮真实上传量，例如「推送 23 条（2.8 MB）」。

## 八、多仓库轮换方案（已实施 · 2026-11-05）

> 触发条件：容量条接近上限（>85% 持续出现）、用户有多账号分仓需求，或实施清单分片（第六节）之前。

### 需求

每端绑定一个仓库列表（最多 5 个），按顺序写满即封存，新上传自动切到下一个库。绑定弹窗加「+」号追加行，每行是 `owner/repo + Token`。

**概念修正**：绑定的单位是「仓库」而不是「Token」——一个 Token 可访问同账号下多个仓库。这样 GitHub（单库 1GB 软限制、库数不限）挂 5 库 ≈ 5GB，Gitee（单库 500MB、总 5GB）挂 5 库正好用满。

### 设计要点

1. **分桶模型**：仓库按绑定顺序排队，`targets[0]` 为活跃库；用量 ≥90% 封存（只读）。每条记录新增 `home`（各端当前住在几号库），删除与回源都按 `home` 定位。
2. **删除扫尾**：只删当前版本所在库的文件。旧版本残留已封存库没有意义——Git 历史本来就不随删除释放配额，不做跨库清扫。
3. **回热（换手机）**：首次同步按顺序读所有活跃库的清单合并（同一条取 `updated` 大者）；已封存库平时不拉取，只在存在待删除记录时扫尾。下载轨迹按「home 库 → 逐库尝试」回源。
4. **兼容迁移**：现有单库配置 → `targets[0]`，零成本；`backup` 位语义不变（「哪一端有」），记录页徽标不用动。
5. **UI**：绑定弹窗改为列表 + 「+」追加行；备份页每库一条容量条 + 端内汇总行；空间预算卡片按活跃库折算。

### 实施范围（动 sync.ts 核心对账）

- `ProviderConfig` → `ProviderTargets { targets: ProviderConfig[]; active: number }`，配置读取处统一迁移。
- `where[provider]` 语义保持「该端最新对账版本」，新增 `meta.home`；`markBacked` 写入 home。
- `runSync`：probe/usage 全量库；pull 只读活跃库 manifest + 有墓碑待扫的库；push 写活跃库，跨过阈值即封存切换。
- `downloadTrack`：home 优先，逐库兜底。
- 回归：sync / delete-sync / space-budget / dist-sync 全链路，外加「封存后切换、旧库扫尾、home 迁移」三个新用例。

### 风险提示

`sync.ts` 是历史上踩坑最多的模块（WebView 缓存 sha、墓碑合并、409 重试都在这），实施前先为现有行为补齐测试快照，改动分两次提交：先加 targets 抽象（行为不变），再加分桶轮换。

### 实施落地记录（2026-11-05）

- `ProviderTargets { targets[], active }` 取代单仓库配置，旧配置读取时自动迁移成 `targets[0]`，上限 `MAX_TARGETS=5`；封存线 90%（`SEAL_RATIO`），停止上传红线 96%。
- `meta.home[provider]` 存 `owner/repo` 键（不存下标——跨设备绑定顺序可能不同），删除与回源按它定位，解析不到退回 0 号库；`markBacked` 写入，`restoreActivity` 清空。
- 引擎：全新设备按队列顺序拉**所有**库的清单合并（活跃库最后读、时间戳最新者胜）；日常只拉活跃库。「远端还有它」只看活跃库清单，封存库清单完全只读。切换持久化到配置并提示。
- 修复连带发现的边角：上传被容量拦住时**不再写清单**——否则清单里的新版本号会让对账误判「已同步」，容量恢复后轨迹永远缺一块。
- UI：绑定表单可编辑活跃库；每端卡片新增「+ 仓库」追加入口（满 5 个隐藏）与仓库队列列表（●活跃 / ○已封存 + 各库用量）；容量条按「队列合计 / 单库上限 × 库数」显示。
- 回归：`tools/multi-repo-test.mjs` 覆盖迁移/封存切换/下载 home 优先/删除精确扫尾/换机拉取/容量汇总，另有 sync / delete-sync / space-budget / backup-adapter / dist-sync 全部通过。
